# imbh-c Development Journal

Append-only chronological log of findings, insights, and decisions for `imbh-c`, the C/C++ FFI
bindings for [IMBH](../imbh). New entries go at the **end**; do not edit existing sections.

---

## 2026-07-22 — Initial C/C++ bindings: ingest, SQL, typed queries over the Arrow C Data Interface

Built `imbh-c` from scratch: a standalone Cargo crate (`crate-type = ["cdylib","staticlib","rlib"]`)
that wraps the IMBH facade in a panic-safe `extern "C"` ABI, with a header-only C++ RAII layer. It
depends on `imbh` by path with `features = ["search", "cdata", "proto"]`, and is deliberately **not**
part of IMBH's workspace — matching IMBH's own design intent (ARCHITECTURE.md §10.17: "the FFI layer
itself … [is] a separate project, out of scope for this repo").

**What was built:**

- `src/lib.rs` — lifecycle (`imbh_db_open_memory` / `imbh_db_open` + options / `close` / `free`),
  OTLP ingest (logs/traces/metrics, raw protobuf bytes), `imbh_db_query_sql`, and ops
  (`flush`/`maintain`/`compact`/`stats`/`table_stats`). One owned current-thread tokio runtime per
  handle drives the async `Db` via `block_on` (C has no async runtime).
- `src/query.rs` — native C query **builders** (`imbh_log_query` / `imbh_metric_query` /
  `imbh_span_metrics_query`) with fluent setters + the `imbh_db_{logs_query,metrics_range,
  traces_span_metrics}` entry points. No protobuf on the public surface (see the pivot below).
- `src/error.rs` — `imbh_error` codes mapped from `imbh::Error` (classifiers first:
  `is_backpressure`/`is_not_found`), thread-local `imbh_last_error_message()`, and a `guard()` that
  wraps every call in `catch_unwind` (IMBH library crates unwind rather than abort).
- `src/arrow_stream.rs` — `Vec<RecordBatch>` → `FFI_ArrowArrayStream` (zero-copy handoff).
- `include/` — cbindgen-generated `imbh.h`, header-only `imbh.hpp` (RAII `Db`/`Stream` + fluent
  query builders), and Arrow's own `arrow/c/abi.h` vendored verbatim.
- `proto/` — version-pinned `.proto` schemas (see finding below), `CMakeLists.txt` + `imbh.pc.in`,
  and C/C++ examples wired into CTest.

**Verification (all green):** `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`,
8 Rust round-trip tests (drive the `extern "C"` surface in-process, re-import the exported
`ArrowArrayStream` with arrow-rs, assert values), and 3 CTest cases (C SQL, C++ SQL+typed builder,
C typed builder) compiled against the built library.

### Findings

- **The `cdata` + `proto` + `blocking()` foundation already exists in IMBH and is stable.** `cdata`
  re-exports `FFI_ArrowArray/Schema/ArrowArrayStream` off the single datafusion-shared arrow instance;
  `proto` adds `imbh::proto::*` wire types, `TryFrom` onto the builders, and the `*_batches` Arrow
  entry points; `blocking()` gives a sync facade. `imbh-c` is purely the greenfield `extern "C"` layer
  on top.
- **Single-arrow rule (critical).** `imbh-c` must never declare its own `arrow` dependency. Every
  Arrow type is named through `imbh::arrow` / `imbh::FFI_*` so exactly one arrow crate is linked and
  the FFI structs stay ABI-compatible. A second, separately-versioned arrow would silently break the
  boundary.
- **Use Arrow's native C types, not a bespoke copy.** The C surface references
  `struct ArrowArrayStream` from Arrow's own `<arrow/c/abi.h>` (vendored verbatim from the arrow-go
  module cache — Apache-2.0). arrow-rs's `FFI_ArrowArrayStream` is `#[repr(C)]` layout-identical.
  cbindgen must emit the `struct` keyword (Arrow's `abi.h` provides no bare typedef) — achieved with
  `[export.rename] "FFI_ArrowArrayStream" = "struct ArrowArrayStream"` + `export.exclude`.
- **OTLP `.proto` files must be version-pinned to the Rust side.** IMBH decodes OTLP with
  `opentelemetry-proto` **0.32.0**, whose CHANGELOG records "Update proto definitions to **v1.10.0**",
  and which *ships those exact `.proto` files* at `src/proto/opentelemetry-proto/`. We vendor those
  files verbatim (logs/traces/metrics + `common`/`resource` + collector services; skipped
  `profiles/v1development`), so consumer-generated ingest stubs are wire-compatible by construction.
  Re-vendor whenever IMBH bumps that dep. Documented in `proto/VERSIONS.md`.
- **cbindgen does not expand macros.** Functions generated by a `macro_rules!` are invisible to
  cbindgen and silently missing from the header. All `#[no_mangle]` entry points must be written out
  explicitly (macros are fine inside function *bodies*, which cbindgen doesn't parse).
- **C namespace collision.** A `typedef struct X` and a function `X` are both ordinary C identifiers
  and collide — Rust allows a struct and fn to share a name, C does not. Renamed the stats struct to
  `imbh_stats` so the `imbh_db_stats()` function keeps its name.
- **Result columns aren't plain `Utf8`.** DataFusion 54 emits `Utf8View`, and IMBH dictionary-encodes
  `service`; tests must `arrow::compute::cast(col, &DataType::Utf8)` before downcasting to
  `StringArray`, rather than assume an encoding.
- **`query_batches` returns no schema for empty results** (unlike `collect_with_schema`). Added
  `arrow_stream::export_batches_infer` that takes the schema from the first batch, falling back to an
  empty schema — a documented edge case for the typed endpoints.

### Decisions

- **Public query surface is native C builders, not raw proto bytes.** First cut passed
  protobuf-encoded query bytes across the ABI; that forces a C consumer to link a protobuf library and
  hand-serialize — defeating the point of an in-process binding. Pivoted to opaque builders
  (`imbh_log_query_new` → setters → `imbh_db_logs_query` → `imbh_log_query_free`), backed internally by
  IMBH's proto messages + validated `TryFrom` (so severity-range / enum / overflow narrowing is
  reused), but exposing no protobuf. The `proto/` schemas remain bundled for consumers that *want*
  protobuf (out-of-process senders, ingest-payload construction).
- **Ingest stays OTLP-bytes.** That is IMBH's wire contract and exactly what any OTLP/HTTP exporter
  emits; a native builder there would be re-inventing OTLP.
- **Builder handles are heap-allocated (`new`/`free`), by choice.** Considered bring-your-own-storage.
  A POD `#[repr(C)]` descriptor of borrowed pointers *would* be sound here — the query is consumed
  synchronously and deep-copied inside the call, so borrowed data need only live for the call's
  duration — but it trades away incremental `add_*` ergonomics and the fully-hidden ABI-stable layout.
  Placement-into-opaque-storage BYOS is unattractive: the builder wraps a non-POD Rust type
  (`Vec`/`String`), so it would still need an explicit destroy (Drop) and still allocate internally,
  saving only one small malloc. Kept the opaque builder; user confirmed.

### Follow-ups (out of scope for this cut)

- Only 3 of IMBH's 8 typed surfaces have `*_batches` entry points upstream; metric-points,
  histogram-quantile, and trace-search/assembly are materialize-only in IMBH today and would need
  Rust-side work before a binding.
- `metrics_range` / `traces_span_metrics` compile and have C/C++ builders but only the logs path has an
  automated end-to-end test (identical, tested pattern).
- Arrow-IPC-bytes fallback for consumers without a C Data Interface importer; snapshot/export and
  read-only multi-process reader helpers.
- Header freshness is enforced by build.rs regenerating `include/imbh.h`; CI should
  `cargo build && git diff --exit-code include/imbh.h`.

## 2026-07-25 — Upstream published to crates.io (v0.1.0) + full `imbh-go` surface parity

IMBH was officially released to crates.io at **v0.1.0** (12 crates; `imbh-test-support` stays
dev-only). This session (a) reflected the upstream API changes that reached `imbh-c`, then (b) grew
`imbh-c` from the ingest/SQL/typed-query core to the **complete surface the Go binding (`imbh-go`)
exposes**, and (c) ran a fidelity audit against `imbh-go` to close the last gaps. End state: **98**
exported functions/structs, **21** Rust round-trip tests, clippy clean, C++ header compiles, all
**33 imbh-go ops** covered.

**Dependencies.** `imbh` is now `{ version = "0.1", path = "../imbh/crates/imbh", features = [...] }`
— version **and** path, the same pattern IMBH uses for its own internal deps (local checkout builds;
version pins the published API). Added `imbh-lgtm` (`features = ["source"]`) for the query-language
execution traits and `imbh-core` for `canonical_json_object`. All resolve to the one `imbh`/`arrow`
instance already in the graph (single-arrow rule intact).

**Surfaces added (all zero-copy Arrow unless noted):**

- **API-change reflection** (`imbh` 0.0.0→0.1.0): `IngestReceipt.lsn`/`DbStats.durable_lsn` became
  `Option<Lsn>` (`Lsn = NonZero<u64>`); `IngestReceipt.queued` field → `is_queued()` method;
  `logs().query_batches` split into `query_batches` (no stats) + `query_batches_with_stats`.
- **LGTM query languages** (`src/lgtm.rs`): `imbh_db_query_{promql,logql,traceql}` + `imbh_db_get_trace`,
  via `imbh-lgtm`'s `translate_*` + `execute_*_batches`.
- **Discovery / aggregation** (`src/discovery.rs` + query.rs): `attr_names`, `attr_values`,
  `metric_catalog`, `metric_series`, `metric_exemplars`, `metrics_instant`, `logs_volume`.
- **Trace search / metric points / paged logs / count**: `imbh_db_traces_search` (proto `TraceQuery`
  builder), `imbh_db_metrics_points` (native `MetricPointsQuery` builder), `imbh_db_logs_page`,
  `imbh_db_logs_count`.
- **Admin / snapshot / export / IPC / read-only** (lib.rs): `imbh_db_snapshot`,
  `imbh_db_durable_through`, `imbh_db_segments`, `imbh_db_segment_files`, `imbh_db_export`,
  `imbh_db_query_sql_ipc`, `imbh_db_open_read_only`, plus the `imbh_bytes` owned-buffer type +
  `imbh_bytes_free`. Extended `imbh_open_options` to the full builder surface (memory budget, retention,
  max-disk, refresh policy, background maintenance, promote-keys).
- C++ RAII wrappers for every new surface (`TraceQuery`/`MetricPointsQuery`/`Bytes` classes + `Db`
  methods); README sections for each.

### Findings

- **`NonZero` LSNs make `0` a free sentinel.** `IngestReceipt.lsn`/`durable_lsn`/`durable_through` are
  `Option<Lsn>` with `Lsn = NonZero<u64>`, so a real LSN is always ≥ 1. The C ABI keeps a plain `u64`
  and maps `None → 0` with no ambiguity (`lsn.map_or(0, |l| l.get())`). Preserves the existing struct
  layout — the committed header didn't change for the reflection.
- **`imbh-lgtm` needs the `source` feature** for the `*SemanticsExt` execution traits
  (`execute_{promql,logql,traceql}_batches`); parse-only consumers stay free of the DataFusion/Tantivy
  subtree. It depends on the same `imbh`, so no second arrow is linked.
- **The LGTM series-column naming is inconsistent upstream, and that's faithful.** PromQL / range-LogQL
  stream `imbh-lgtm`'s own batch `labels | ts | value` (`ts` a Timestamp), while `metrics_instant` /
  `logs_volume` hand-build `labels | timestamp | value` (Int64) / `bucket_time | labels | count`.
  `imbh-go` has the exact same split; `imbh-c` reproduces it deliberately rather than "fixing" it.
- **Most discovery handlers hand-build the Arrow batch** from materialize-returning facade methods
  (`attrs().names()`, `metrics().catalog()/series()/exemplars()`, `traces().search()`,
  `logs().volume_by()`) — only `metric_points` uses a real upstream `*_batches`. Label columns are
  IMBH's `canonical_json_object` (keys sorted, byte-stable) so they join across results; that pulled in
  a direct `imbh-core` dep (same crate already in the graph).
- **Paged logs need no opaque cursor.** `PageCursor(pub(crate) usize)` isn't constructible outside the
  `imbh` crate and its serde is feature-gated — but `LogQuery::after(cursor)` just sets `self.offset`,
  and the proto/builder already exposes `offset` (`imbh_log_query_set_offset`). So `imbh_db_logs_page`
  is plain **offset paging**: override `proto.offset = after`, run `query_batches_with_stats`, and
  return `next_offset = after + rows_returned` with `has_more = limit > 0 && rows_returned >= limit`
  (matching `imbh-go`'s derivation). `imbh-go`'s out-of-band `OP_LOG_PAGE_META` folds into `stats` /
  `next_offset` / `has_more` out-params.
- **`metric_points` has no proto message**, so its builder is native-backed (stash metric/kind/filters/
  range/limit, assemble the fluent `MetricPointsQuery` at run time) — the one builder that isn't
  proto+`TryFrom`. `trace_search` **does** have a proto `TraceQuery` + `TryFrom`, so it mirrors the
  `imbh_log_query` pattern exactly.
- **`imbh::arrow::ipc` is available even though IMBH's direct `arrow` dep only declares `ffi`.**
  DataFusion (pulled by `query`) enables `arrow/ipc` and feature unification is a superset, so
  `StreamWriter`/`StreamReader` compile. `encode_ipc` is how `Db::export` produces its bytes, reused
  for the SQL→IPC fallback.
- **Owned byte buffers across FFI**: `imbh_bytes { data, len }` from `Vec<u8>::into_boxed_slice()` +
  `Box::into_raw`; free reconstructs via `ptr::slice_from_raw_parts_mut` (not `slice::from_raw_parts_mut`
  — clippy `cast_slice_from_raw_parts`) and is a no-op for `len == 0` (empty boxed slice never
  allocates).

### Fidelity audit vs `imbh-go` (the re-check)

Cross-checked all **33 ops** and all **47 public `DB` methods**. Two real gaps, both closed:

- **`logs().count()`** (op 33 / `CountLogs`) was missing → `imbh_db_logs_count` (reuses `imbh_log_query`;
  `SELECT count(*)` over the filter, ignoring limit/offset/direction).
- **`imbh_open_options` was missing 6 `DbOptions` fields** → added `memory_budget_bytes`,
  `retention_days`, `max_disk_bytes`, `maintenance_background_ms`, a `refresh` policy
  (`imbh_refresh_mode` + `refresh_ttl_ms`), and `promote_keys` (`*const *const c_char` + len).
  `build_options` now applies them; every numeric field treats `0` as "IMBH default".

Verified as **non-gaps**:

- **`TryIngestOTLP*`** is a **sable-transport** distinction (`Call` vs `TryCall` on the Go dispatch
  queue). Both `imbh-go` variants hit `db.ingest_otlp_logs(body).await` — exactly what `imbh-c` calls.
  There is no intermediary queue in the direct-FFI model, so the "try" variant has no meaning here.
- **`*Typed` / `*Series` / `*Lines` / `*Matches` / `ExportRecords` / `GetTraceSpans` / `GetTraceForest`**
  are Go-side *decoders* over the Arrow results, not distinct ops. `imbh-c` returns the same Arrow;
  decoding is the C consumer's job.
- **`LogVolume` / `LogVolumeBy`** both covered by one `imbh_db_logs_volume` (empty group-by = ungrouped).

### Decisions

- **`CallError::Query` variant** added so LGTM translate/eval failures (bad query text, unresolved
  metric, out-of-order range) map to `IMBH_ERROR_QUERY`, kept distinct from `INVALID_ARG` (null/garbage
  pointer = binding misuse).
- **Interval units stay milliseconds.** `refresh_ttl_ms` / `maintenance_background_ms` use ms to match
  the existing `wal_interval_ms`, whereas `imbh-go`'s wire uses ns. A deliberate, internally-consistent
  convention difference (sub-ms intervals aren't expressible — acceptable for these knobs).
- **Segments / segment-files return Arrow streams**, not a POD array + count, matching the rest of the
  binding (list results are Arrow).
- **`imbh_db_logs_query` keeps writing `stats`** (via `query_batches_with_stats`) even though
  `imbh-go`'s `OP_QUERY_LOGS` uses the no-stats `query_batches` — a strict superset, not a divergence.

### Follow-ups

- The previous cut's follow-ups are **all done**: metric-points / trace-search now have entry points
  (native builder / hand-built batch), and the Arrow-IPC fallback + snapshot/export/read-only helpers
  ship. **No known gaps against `imbh-go` remain.**
- Minor known difference (intentional): ns-precision WAL/refresh/maintenance intervals aren't
  expressible (the C options use ms).

## 2026-07-25 — CD/release workflow: static + dynamic libs per arch/OS

Added `.github/workflows/release.yml` (display name `CD`) — the project's first CI/CD. It builds both
the dynamic-link library (`.so`/`.dylib`/`.dll`) and the static archive (`.a`/`.lib`) for every supported
architecture/OS, uploads them as workflow artifacts on every push/PR, and attaches packaged archives to a
GitHub Release on `v*` tags. This is greenfield: no prior CI existed and the repo is not yet under git, so
the workflow only starts running once `imbh-c` is pushed to GitHub.

### Design decisions (chosen with the user)

- **Resolve IMBH from crates.io, not the `../imbh` sibling.** `Cargo.toml` declares `imbh`, `imbh-lgtm`,
  `imbh-core` as `{ version = "0.1", path = "../imbh/crates/..." }`; that sibling checkout does not exist
  in CI. A cross-platform `sed` step (`shell: bash`, works on GNU/BSD/git-bash) strips the `path = "..."`
  attribute before building, leaving `version = "0.1"` + features so Cargo pulls the published `0.1.0`
  crates. CI-only — the committed manifest keeps the path override for local dev. Alternative (co-checkout
  the sibling repo) was rejected as heavier and needing cross-repo access.
- **Target matrix (7), native runners + zigbuild for Linux cross:**
  x86_64/aarch64 `linux-gnu` **and** `linux-musl` (all four via `cargo zigbuild` on one `ubuntu-latest`),
  x86_64 (cross) + aarch64 (native) `apple-darwin` on `macos-14`, x86_64 `pc-windows-msvc` on
  `windows-latest`.
- **Trigger = tag Release + CI artifacts:** builds on push/PR upload artifacts; `v*` tags additionally
  publish a Release with `SHA256SUMS`.

### Findings

- **The build is hermetic — cross-compilation is feasible with only a C toolchain per target.** protobuf
  is pure-Rust (`protox`, confirmed in `../imbh/crates/imbh-proto/build.rs` — no system `protoc`), cbindgen
  is pure-Rust, and the only native C compiled is vendored zstd/lz4 via `cc`. No OpenSSL/ring/protobuf-src
  in the graph. `cargo-zigbuild` supplies the cross C toolchain for the four Linux gnu+musl targets from a
  single runner; Apple clang cross-compiles the x86_64 darwin target on the arm64 runner.
- **crates.io resolution verified** (dry-run in scratch): after the strip-path `sed`,
  `cargo generate-lockfile` resolved `imbh 0.1.0` / `imbh-core 0.1.0` / `imbh-lgtm 0.1.0` from the registry
  (382 packages, Rust 1.96) with the requested features. Did not run the full cold build (multi-minute
  DataFusion compile); the real build runs in CI.
- **Header-freshness gate now has a home** (closes the recurring `TODO.md` ask). The `verify` job runs
  `cargo build --release` then `git diff --exit-code include/imbh.h`. This is a *separate* gate because
  `build.rs` swallows cbindgen errors as warnings. It targets the header path only, since the strip-path
  step intentionally dirties `Cargo.toml`.
- **Windows library naming:** MSVC emits `imbh_c.dll` + import lib `imbh_c.dll.lib` + static `imbh_c.lib`
  (distinct names, no collision). The package step globs whichever of the known lib filenames exist and
  fails if none are found.
- **`Cargo.lock` is `.gitignore`d**, so each run resolves fresh from crates.io; the resolved lock is not
  currently shipped (a reproducibility gap — see follow-ups).
- All actions are SHA-pinned. Reused the vetted SHAs from `../imbh/.github/workflows/` (checkout v7.0.1,
  rust-toolchain, rust-cache v2.9.1, taiki-e/install-action v2.85.0, upload-artifact v7.0.1); resolved
  current SHAs for `download-artifact` v8.0.1, `softprops/action-gh-release` v2.6.2, `mlugg/setup-zig`
  v2.2.1. Validated with `actionlint` v1.7.7 (no issues).

### Follow-ups

- **CMake/CTest example smoke is out of scope** for this workflow (needs the shared lib at the exact
  `target/release/` path); add later as a separate CI job if desired.
- **No `LICENSE` file at repo root** (crate is Apache-2.0); the package step copies it only if present.
  Add an Apache-2.0 `LICENSE` so it ships in the archives.
- **Reproducibility:** consider committing/shipping the CI-resolved `Cargo.lock` as a release asset and
  building with `--locked` to pin exact `imbh`/DataFusion versions per release.
- The sanitizer (ASAN/LSan) gate over the FFI ownership path is still pending and not covered here.

## 2026-07-25 — GitHub Actions dependency freshness audit

Audited every action pinned in `.github/workflows/release.yml` against the GitHub API to confirm each
SHA-pin still tracks the latest upstream release. Convention preserved: SHA pin + trailing `# vX.Y.Z`
version comment on every `uses:`.

### Findings

- 7 of 8 actions were already at the latest release: `actions/checkout` v7.0.1,
  `Swatinem/rust-cache` v2.9.1, `mlugg/setup-zig` v2.2.1, `taiki-e/install-action` v2.85.0,
  `actions/upload-artifact` v7.0.1, `actions/download-artifact` v8.0.1.
- Only stale pin: **`softprops/action-gh-release` v2.6.2 → v3.0.2**. Updated the SHA to
  `3d0d9888cb7fd7b750713d6e236d1fcb99157228`. The published tag `v3.0.2` is an *annotated* tag, so its
  ref object (`fe965f7…`) had to be dereferenced (`git/tags/<sha>` → `.object.sha`) to get the real
  commit SHA — pinning the tag-object SHA would be wrong.
- `dtolnay/rust-toolchain` tracks the rolling `stable` ref (no semver release). Its current tip SHA
  (`commits/stable`) still equals the pinned `4cda84d5c5c54efe2404f9d843567869ab1699d4` — no change.
- `taiki-e/install-action` tags by tool name as well as by version; had to filter tags with
  `select(test("^v[0-9]"))` to find the real semver latest (v2.85.0), which matched the pin.
- v3 of `action-gh-release` is a major bump, but the release step uses only `files`,
  `fail_on_unmatched_files`, and `generate_release_notes` — all unchanged across the v2→v3 boundary, so
  no config migration was needed.

### Method (reusable)

- `gh api repos/<owner>/<repo>/releases/latest --jq .tag_name` for the latest tag.
- For an annotated tag, `gh api repos/<r>/git/refs/tags/<tag>` gives the tag object; when
  `.object.type == "tag"`, deref via `gh api repos/<r>/git/tags/<sha> --jq .object.sha` for the commit.
- For rolling refs (dtolnay `stable`), compare `gh api repos/<r>/commits/<ref> --jq .sha` to the pin.

## vcpkg + Conan packaging (prebuilt-binary distribution)

Made the binding installable through **vcpkg** and **Conan**, both consuming the *prebuilt* per-target
archives `release.yml` already attaches to each GitHub Release (no Rust toolchain needed to consume).
Both expose the identical CMake target `imbh-c::imbh-c`, so downstream `find_package(imbh-c CONFIG)` +
`target_link_libraries(app PRIVATE imbh-c::imbh-c)` is the same regardless of manager.

### Files

- `ports/imbh-c/` — vcpkg port: `portfile.cmake` maps the triplet → Rust target, downloads the
  matching release archive (`vcpkg_download_distfile` + per-target SHA512), installs headers + the
  linkage-appropriate lib into `{,debug/}{lib,bin}`, and `configure_file`s `imbh-c-config.cmake.in`
  into `share/imbh-c/`. `vcpkg.json` (manifest), `usage`.
- `versions/{baseline.json,i-/imbh-c.json}` — makes the repo a vcpkg **git registry** (must live at
  repo root; a git registry can't point at a subdirectory).
- `packaging/conan/conanfile.py` — Conan 2.x recipe: `package_type = "library"` + `shared` option;

### Design notes

- **Prebuilt, not from-source** (user choice): reuses the existing release artifacts; a cargo
  from-source port would need a Rust toolchain + the full DataFusion tree (minutes) and crates.io
  resolution of the path-overridden `imbh` deps.
- **Checksums are placeholders until a real release exists.** The `v0.0.0` release has no assets, so
  the SHA512/SHA256 tables ship as sentinel `"0"` and both managers refuse to install by design;
  `update-hashes.sh <tag>` finalizes them once assets are published. Release order: tag → build →

- **Static linkage** attaches the canonical `rustc --print native-static-libs` set (Linux

  self-contained (confirmed: `ldd libimbh_c.so` → only libgcc_s/libm/libc) and needs none of these.
- **musl** archives from the release matrix are intentionally not consumed by either package.

## Packaging release automation (one-click bump)

Automated the version-bump + release-finalize flow so a maintainer only chooses the version number.

- `packaging/bump-version.sh <version> [--push|--no-commit|--no-tag|--remote|--branch]` — bumps the
  two source-of-truth files (`Cargo.toml` package version, `imbh.pc.in` `Version:`), stages *only*
  those two (targeted add, so a dirty tree isn't swept in), commits `Bump to X`, tags `vX`, optional
  push. Validates semver-ish + refuses an existing tag.
- `.github/workflows/bump-version.yml` (`workflow_dispatch`, input `version`) — calls
  `bump-version.sh … --push --branch main`. Checkout token is `secrets.RELEASE_PAT || github.token`.
- `.github/workflows/finalize-packaging.yml` — `on: workflow_run: [Release] completed`; for a
  successful tag-triggered run it downloads the assets, runs `update-hashes.sh`, commits the 4
  checksum files, bootstraps vcpkg, runs `vcpkg-add-version.sh`, commits `versions/`, pushes to main.

Two GitHub-token gotchas drove the design (both documented in the workflow headers + packaging README):
1. A tag pushed with `GITHUB_TOKEN` does **not** trigger `release.yml` → bump uses `RELEASE_PAT`.
2. A release published under `GITHUB_TOKEN` does **not** fire a `release` event → finalize triggers on
   `workflow_run` (which does fire) instead of `on: release`.

Kept the logic DRY: the two scripts are exactly what the workflows invoke, so local and CI runs match.
Did not touch the concurrently-edited `release.yml`; added only new workflow files.

Verified `bump-version.sh` in an isolated temp git repo: bumps only the package version (rust-version
and dependency `version = "0.1"` untouched), commit contains exactly the two files, unrelated dirty
files stay out, duplicate-tag + bad-version guards fire, `--no-commit` edits only. Both new workflow
YAMLs parse. Not exercised: an actual Actions run (needs the repo + RELEASE_PAT + a real release).

## Dropped bump-version.yml (CI-created commits deemed unsound)

Removed `.github/workflows/bump-version.yml`. The one-click bump had CI create the version-bump
commit + tag; making those land as *signed/Verified* commits (needed if `main` requires signed
commits) has no sound option here — GPG/SSH key-in-runner and the GitHub-API-signed-commit routes
were all rejected. Version bumping is therefore local-only via `packaging/bump-version.sh` (a pure

`finalize-packaging.yml` remains for now but shares the same auto-commit-to-main property; its fate is
open. README "Releasing" updated to a single local flow.

### Findings (durable)

- **A vcpkg git registry requires `ports/` and `versions/` at the repository root.** There is no way
  to point a git registry at a subdirectory, so the vcpkg port could not be nested under `packaging/`.
- **Prebuilt checksums can only come from real published files.** The `v0.0.0` release exists but has
  no assets, so the SHA512/SHA256 tables ship as sentinel `"0"` and both managers refuse to install by
  design (vcpkg rejects the download hash; Conan raises `ConanInvalidConfiguration`).
  `update-hashes.sh <tag>` finalizes them once assets are published.
- **Rust `staticlib` needs the platform's Rust-std system libraries at final link time**; the cdylib
  does not (confirmed self-contained: `ldd libimbh_c.so` → only libgcc_s/libm/libc). The static path
  attaches the canonical `rustc --print native-static-libs` set: Linux `pthread;dl;m;rt;util`; macOS
  frameworks CoreFoundation/Security/SystemConfiguration; Windows
  kernel32/advapi32/ntdll/userenv/ws2_32/dbghelp/bcrypt/crypt32/secur32/ncrypt.
- **Two GitHub-Actions token rules killed the "one-click" automation** (why bump-version.yml and
  finalize-packaging.yml were dropped): (1) a tag pushed with the built-in `GITHUB_TOKEN` does not
  trigger another workflow, so bump→release needed a PAT; (2) a release published under
  `GITHUB_TOKEN` does not fire a `release` event, so release→finalize had to use `workflow_run`.
- **The real blocker was signed commits.** Any CI job that commits the version bump or the checksums
  must push to `main`; if `main` requires signed commits, the bot commit must be signed, and none of
  the routes (GPG/SSH key-in-runner, GitHub-API-signed commit) were acceptable. Resolution: no CI
  writes to the repo — the maintainer makes and signs every release commit locally.
- **`release.yml` already emits `SHA256SUMS`** (Conan's digest) but not `SHA512SUMS` (vcpkg's). A
  future optimization is to publish both so `update-hashes.sh` reads the sums instead of
  re-downloading + rehashing every archive. Not done, to avoid editing the concurrently-modified
  `release.yml`; the current flow is correct without it.
- **Windows import-lib naming**: cargo emits `imbh_c.dll.lib` (import) alongside `imbh_c.lib`
  (static). The port keeps the `.dll.lib` name and points `IMPORTED_IMPLIB` at it; the Conan recipe
  renames it to `imbh_c.lib` so a bare `libs=["imbh_c"]` resolves. Two different conventions, same
  underlying file.
