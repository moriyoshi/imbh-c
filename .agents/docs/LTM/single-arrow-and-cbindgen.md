# Single-arrow rule, cbindgen, and header generation

## Summary

Two build-time constraints keep the C boundary sound: exactly one `arrow` crate must be linked (the single-arrow rule), and the generated `include/imbh.h` must faithfully reflect the `extern "C"` surface. cbindgen has sharp edges around macros and naming that shape how the surface is written.

## Key Facts

- **Single-arrow rule (critical).** imbh-c never declares its own `arrow` dependency. Every Arrow type is named through `imbh::arrow` / `imbh::FFI_*`, so exactly one arrow crate is linked and the FFI structs stay ABI-compatible with the consumer's Arrow. A second, separately-versioned arrow would silently break the boundary. `imbh-lgtm` and `imbh-core` depend on the same `imbh`, so no second arrow enters the graph.
- **cbindgen does not expand macros.** Functions generated by a `macro_rules!` are invisible to cbindgen and silently missing from the header. Every `#[no_mangle] pub extern "C"` entry point must be written out explicitly. Macros are fine *inside* function bodies (cbindgen doesn't parse those).
- **Use Arrow's native C types, not a bespoke copy.** The surface references `struct ArrowArrayStream` from Arrow's own `<arrow/c/abi.h>`. cbindgen must emit the `struct` keyword (Arrow's `abi.h` provides no bare typedef) — achieved with `[export.rename] "FFI_ArrowArrayStream" = "struct ArrowArrayStream"` plus `export.exclude`.
- **C namespace collision.** In C, a `typedef struct X` and a function `X` are both ordinary identifiers and collide (Rust allows a struct and fn to share a name; C does not). The stats struct is named `imbh_stats` so the `imbh_db_stats()` function keeps its name.

## Details

- `include/imbh.h` is regenerated from the `extern "C"` surface by cbindgen via `build.rs` on every `cargo build`. The header is committed, so after a build it must match the generated output.
- Header freshness is meant to be CI-enforced with `cargo build && git diff --exit-code include/imbh.h` once the project is under git (see `TODO.md`). The round-trip test `committed_header_has_key_symbols` guards a subset of symbols, but a fresh `cargo build` is the source of truth.
- The `cdata` + `proto` + `blocking()` foundation lives in IMBH and is stable: `cdata` re-exports `FFI_ArrowArray/Schema/ArrowArrayStream` off the single datafusion-shared arrow; `proto` adds `imbh::proto::*` wire types, `TryFrom` onto the builders, and the `*_batches` Arrow entry points; `blocking()` gives a sync facade. imbh-c is purely the greenfield `extern "C"` layer on top.

## Files

- `build.rs` — drives cbindgen to (re)generate `include/imbh.h`.
- `cbindgen.toml` — the `export.rename` / `export.exclude` config for `struct ArrowArrayStream`.
- `include/imbh.h` — generated + committed C header.
- All `src/*.rs` — every `pub extern "C" fn` is written out explicitly.

## Test Coverage

- `tests/roundtrip.rs::committed_header_has_key_symbols` — asserts key symbols are present in the committed header.

## Pitfalls

- Adding a new entry point behind a `macro_rules!` → it silently vanishes from the header. Write it out.
- Naming a struct the same as a function → C compile error in the consumer. Suffix the struct (`imbh_stats`).
- Depending on `arrow` directly, or letting a transitive dep pull a second arrow version → ABI mismatch at the boundary. Route every Arrow type through `imbh::`.
- Forgetting to commit a regenerated `include/imbh.h` after changing the surface → stale header ships.
