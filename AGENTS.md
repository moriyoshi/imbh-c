# Rules and protocols

## General

* imbh-c is a C/C++ FFI binding of IMBH (`../imbh`, a Rust embeddable observability DB). It is a thin, panic-safe `extern "C"` ABI (plus a header-only C++ RAII wrapper in `include/imbh.hpp`) built directly on IMBH's synchronous `blocking()` facade — C has no async runtime, so each handle owns one current-thread tokio runtime and drives the async `Db` via `block_on`. There is no sable, no goroutine scheduler, and no cgo: the boundary is a plain C ABI. Query results cross that boundary zero-copy as an Arrow `struct ArrowArrayStream` (the Arrow C Data Interface). Read `README.md` (as-built) before changing the ABI surface, the batch handoff, or the ownership model.
* The project is one Cargo crate (`crate-type = ["cdylib", "staticlib", "rlib"]`) that wraps the IMBH facade: the `.so`/`.dylib`/`.dll` is self-contained, the `.a` is for static linking into a C/C++ host, and the `rlib` lets the crate's own Rust integration tests (`tests/roundtrip.rs`) drive the `extern "C"` surface in-process. `include/imbh.h` is generated from the `extern "C"` surface by cbindgen (via `build.rs`) on every build. The C++ examples build through `CMakeLists.txt` and run under CTest.
* The binding consumes IMBH as a `version` + `path` dependency (`imbh = { version = "0.1", path = "../imbh/crates/imbh", features = ["search", "cdata", "proto"] }`) plus `imbh-lgtm` (`features = ["source"]`) and `imbh-core` — the same pattern IMBH uses for its own internal deps: the local checkout at `../imbh` builds, while the version requirement pins the published API this binding was written against. When you land an upstream change in `../imbh`, re-pin the version (and re-vendor the `proto/` schemas if IMBH bumped `opentelemetry-proto`) rather than drifting.
* **Single-arrow rule (critical).** Never declare a direct `arrow` dependency. Every Arrow type is named through `imbh::arrow` / `imbh::FFI_*`, so exactly one arrow crate is linked and the FFI structs stay ABI-compatible with the consumer's Arrow. A second, separately-versioned arrow would silently break the boundary. `imbh-lgtm` and `imbh-core` depend on the same `imbh`, so no second arrow enters the graph.
* **cbindgen does not expand macros.** Functions generated by a `macro_rules!` are invisible to cbindgen and silently missing from `include/imbh.h`. Every `#[no_mangle] pub extern "C"` entry point must be written out explicitly (macros are fine inside function bodies, which cbindgen doesn't parse).

## Building

* Rust: `cargo build --release` produces `target/release/libimbh_c.{so,a}` and regenerates `include/imbh.h` via `build.rs`/cbindgen. A cold build pulls the full DataFusion tree and takes minutes; the static archive is large. Build it before running the CMake examples, which link it.
* Run `cargo fmt` on the crate before reporting a change as done.
* The standard local gate for any change you make — this applies to subagents too:
  ```
  cargo fmt --check
  cargo build --release
  cargo clippy --all-targets --release -- -D warnings
  cargo test --release                        # tests/roundtrip.rs drives the extern "C" surface

  # C/C++ examples (when the ABI, header, or examples changed)
  cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
  cmake --build build
  ctest --test-dir build --output-on-failure
  ```
  Fix violations and re-run until clean. Do not declare a change complete with a failing fmt, build, clippy, tests, or CTest.
* **Header freshness.** `include/imbh.h` is generated and committed. After a build, it must match the generated output. When adding or changing an `extern "C"` entry point, rebuild and confirm the header regenerated to include it — the round-trip test `committed_header_has_key_symbols` guards a subset, but a fresh `cargo build` is the source of truth.

## Testing

* Make sure regression tests are ready for your fix.
* The load-bearing tests live in `tests/roundtrip.rs`: they call the `extern "C"` surface in-process, re-import the exported `struct ArrowArrayStream` with arrow-rs, and assert values. Extend them whenever you touch the ABI, a query builder, the batch handoff, or error mapping.
* **Ownership model.** Result batches are owned, segment-independent Arrow allocations handed out behind an `FFI_ArrowArrayStream`; the consumer frees them through the stream's `release` callback (and `imbh_bytes` buffers via `imbh_bytes_free`). There is no Go-style two-free split. Any change to the handoff must keep an empty result carrying its typed schema (see `empty_result_still_has_schema`) and must not leave the stream valid-but-dangling after the DB reclaims segments.
* A sanitizer (ASAN/LSan) gate over the FFI ownership path is still pending; prefer designing new FFI tests so they can also run under a sanitizer, and record the gap in `TODO.md` rather than assuming it is covered.
* Tests must run without external daemons or network. IMBH runs in-process (in-memory or a local segment store); do not introduce tests that need a live service. On-disk lifecycle tests use `tempfile` scratch dirs.

## Shell Pitfalls (prezto defaults)

The user's shell uses prezto, which sets aliases and options that break non-interactive scripts:

* ❌ `cp src dst` prompts interactively when `dst` exists (prezto aliases `cp` to `cp -i`). Always `rm -f dst` before `cp`.
* ❌ `cat > file <<'EOF'` and `echo > file` fail with `file exists` when the target exists (prezto enables `NO_CLOBBER`). Workaround: `rm -f file` before writing, or use `tee` / `/bin/cat`.
* ❌ `rm file` prompts for confirmation on some files (prezto aliases `rm` to `rm -i`). Always use `rm -f` for non-interactive deletion.
